# Migration Stage 1 report: PostgreSQL backend foundation

Date: 2026-08-21. Branch: `feat/ru-infrastructure`.

## Outcome and scope boundary

Stage 1 adds an infrastructure-neutral PostgreSQL 16 baseline and standalone Node backend shell. It does not route application traffic to the new backend. The Vite frontend, Supabase browser repositories, Supabase Auth screens/session flow, Vercel handlers, and DeepSeek handlers/prompts remain unchanged. No Supabase, Timeweb, Vercel, S3, DNS, or other external resource was contacted or mutated.

## Pinned dependencies

- `better-auth` `1.7.1` (exact production dependency); npm marked this as `latest` and it was the highest stable 1.7.x release at implementation time.
- `pg` `8.23.0` (exact production dependency).
- `auth` `1.7.1` (exact development dependency), the matching Better Auth CLI used for reproducible schema generation.

No ORM, backend framework, router, or migration framework was introduced. Node's built-in HTTP server is sufficient for the Stage 1 health shell. The existing ESM convention is retained.

## Migration layout

1. `db/migrations/001_better_auth_1_7_1.generated.sql`
   - creates the dedicated `auth` schema and sets `search_path`;
   - contains SQL generated by the pinned `auth@1.7.1` CLI from `server/auth.js`;
   - creates only `auth."user"`, `auth."session"`, `auth."account"`, and `auth."verification"` plus the generated indexes;
   - uses PostgreSQL UUID IDs because `advanced.database.generateId` is explicitly `"uuid"`;
   - enables the future email/password schema with required email verification and `revokeSessionsOnPasswordReset: true`;
   - can be regenerated with `npm run db:generate-auth-schema` and verified without rewriting with `npm run db:check-auth-schema`.
2. `db/migrations/002_app_baseline.sql`
   - creates the empty greenfield application schema in `public` after the auth identity exists;
   - contains no data copy and no old Supabase migration history.

The Better Auth CLI normally introspects PostgreSQL even for SQL generation. No disposable PostgreSQL service was present. The generation-only config therefore supplies an empty, read-only introspection surface reporting `search_path=auth`; the pinned CLI still owns and compiles every generated table, column, constraint, and index. The committed preamble that creates/selects `auth` is explicitly identified as Kubiki-owned. The reproducibility check compares the committed artifact byte-for-byte after line-ending normalization.

## Application baseline

`public.users` is deliberately thin:

```sql
id uuid primary key references auth."user"(id) on delete cascade,
created_at timestamptz not null default now()
```

The shared primary key and cascading FK enforce a 1:1 auth/application identity relationship. All 12 business ownership FKs reference `public.users(id)`. No business table references Better Auth session, account, or verification state.

The baseline creates `projects`, `performers`, `quick_access_items`, `template_libraries`, `ai_settings`, `studio_export_profiles`, `export_presets`, `ai_usage_events`, `product_events`, `user_flags`, `ai_usage_limits`, and `beta_feedback`. It preserves the Stage 0 columns, defaults, UUID PKs, uniqueness, checks, JSONB fields, ordinary indexes, `set_updated_at()`, the seven required triggers, and the composite quick-access-to-performer FK. It deliberately excludes `public.profiles`, Supabase `auth.users`, RLS/policies, `anon`/`authenticated` grants, Supabase Storage objects, and `handle_new_user()`.

For an explicitly provisioned empty PostgreSQL 16 database, apply with a migration/admin credential separate from the runtime credential:

```sh
psql "$MIGRATION_DATABASE_URL" -v ON_ERROR_STOP=1 -f db/migrations/001_better_auth_1_7_1.generated.sql
psql "$MIGRATION_DATABASE_URL" -v ON_ERROR_STOP=1 -f db/migrations/002_app_baseline.sql
```

No integration apply was performed in Stage 1 because no disposable PostgreSQL was available and mutating a developer or external database was prohibited. Static tests validate ordering, complete table inventory, auth model inventory, FK targets, checks, indexes, triggers, and generated-schema reproducibility.

## PostgreSQL connection and server shell

`server/db.js` creates one long-lived `pg.Pool` with `max: 5`, `idleTimeoutMillis: 30000`, and `connectionTimeoutMillis: 5000`; it exposes explicit pool shutdown. Runtime credentials enter only through backend `DATABASE_URL` and are never imported by Vite/client code.

`server/index.js` starts the framework-free long-running service using `npm run backend:start`. It binds to `PORT` with development fallback `3000`, and to `HOST` with localhost fallback `127.0.0.1`. `/healthz` is process-only. `/readyz` runs parameter-free `select 1 as ready` with a bounded default two-second application timeout and returns no exception/configuration details. Requests have an explicit default 1 MiB body limit. `SIGTERM` and `SIGINT` stop accepting traffic and close the shared pool.

Backend-only environment placeholders are in `.env.example`:

- required to start the shell: `DATABASE_URL`;
- required when the Better Auth config is loaded in Stage 2: `BETTER_AUTH_SECRET` (minimum 32 characters) and absolute `BETTER_AUTH_URL`;
- optional: `PORT`, `HOST`, `BACKEND_BODY_LIMIT_BYTES`, `READINESS_TIMEOUT_MILLIS`.

Their absence does not affect current frontend development, tests, or Vercel builds.
